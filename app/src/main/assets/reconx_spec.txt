RECONX — ULTIMATE ATTACK-SURFACE INTELLIGENCE PLATFORM

Master Engineering Prompt for Claude Code

You are a principal cybersecurity engineer, security architect, senior Python developer, full-stack engineer, and DevSecOps specialist. Your task is to design and build ReconX, a modular, enterprise-grade attack-surface intelligence and defensive security assessment platform.

ReconX should combine passive OSINT, authorized active reconnaissance, asset discovery, safe vulnerability assessment, cloud and container security posture analysis, authentication configuration auditing, evidence management, AI-assisted triage, visualization, and professional reporting in one extensible application.

Build a real, functioning application—not a static mockup, prototype-only interface, or collection of disconnected scripts. It must be maintainable, testable, documented, secure by design, and suitable for deployment on a developer's local machine or an authorized security team's infrastructure.

---

1. PRODUCT VISION

Create a centralized platform that allows an authorized security team to:

- Create and manage security engagements.
- Define and verify authorized targets and exclusions.
- Discover domains, subdomains, IP addresses, services, applications, APIs, and cloud assets.
- Enrich discovered assets with public intelligence and historical observations.
- Perform bounded, non-destructive security checks against approved assets.
- Correlate observed software and configurations with known vulnerability intelligence.
- Review authentication, authorization, cloud, container, and infrastructure security posture.
- Visualize relationships and changes across the attack surface.
- Track findings, evidence, remediation, and retesting.
- Generate professional reports for technical teams, management, and clients.
- Run repeatable scans through a modular plugin framework and CI/CD integrations.

The product should feel like a polished commercial security platform, with a responsive dashboard, clear workflows, live task status, detailed findings, and an intuitive investigation experience.

Operating principles

1. Passive-first reconnaissance.
2. Explicit authorization for every active assessment.
3. Scope validation before every network interaction.
4. Non-destructive checks by default.
5. Read-only access to external cloud resources unless a separately approved integration explicitly supports a safe write operation.
6. Evidence-backed findings with transparent confidence levels.
7. No collection or display of secrets unless explicitly provided by the asset owner for a controlled analysis, and then only with secure handling and redaction.
8. No automated compromise, account takeover, persistence, or data extraction.
9. Clear separation between production assessment and isolated laboratory research.
10. Every module must be independently testable, configurable, auditable, and replaceable.

3. ENGAGEMENT VAULT AND SCOPE FIREWALL

Build an engagement management system as the foundation of the platform.

Engagement Vault

Each engagement should contain:

- Engagement name and unique identifier
- Client or internal team
- Description and business purpose
- Authorization reference and sign-off status
- Start and end dates
- Approved domains, IP ranges, URLs, cloud accounts, repositories, and environments
- Explicit exclusions
- Permitted assessment modules
- Rate and concurrency limits
- Approved testing windows
- Data retention policy
- Engagement owner and authorized operators
- Audit history
- Findings, assets, tasks, evidence, and reports

Support PostgreSQL in production and SQLite for local development. Encrypt sensitive configuration and evidence at rest using an established cryptographic library and managed keys. Do not invent custom cryptography.

Scope Firewall

Implement a central scope-validation service used by every active module.

It must:

- Validate every target before an active request or scan.
- Support exact domains, approved subdomains, IP addresses, CIDR ranges, and explicit URLs.
- Respect exclusions and deny-by-default rules.
- Resolve hostnames safely and validate resolved addresses against scope.
- Revalidate redirects and prevent a request from following a redirect outside the approved scope.
- Guard against DNS rebinding and unexpected resolution changes.
- Block private, link-local, loopback, and metadata-service destinations unless the engagement explicitly authorizes the relevant controlled environment.
- Apply per-module request rates, concurrency caps, and scan budgets.
- Support pause, cancellation, emergency stop, and operator review.
- Record the scope decision for each active task.

If scope cannot be verified, do not proceed with the active operation. Display a clear explanation and request correction by an authorized operator.

Scope Sign-Off

Provide an authorization workflow with:

- Uploadable authorization documents
- Engagement owner approval
- Digital sign-off integration where configured
- Timestamped approval history
- Scope-change history
- Approval expiration
- Reapproval when material scope changes occur

Do not present a checkbox as legal proof of authorization. Clearly distinguish an operator's recorded declaration from independently verified authorization.

4. CORE INFRASTRUCTURE AND TASK ORCHESTRATION

Implement a robust task system.

Task Orchestrator

Use Celery with Redis, or RQ if a simpler implementation is justified.

Features:

- Background task execution
- Task queues by module and priority
- Retry policies for transient errors
- Cancellation and pause support
- Per-engagement concurrency limits
- Per-target rate limits
- Worker health monitoring
- Task progress and structured logs
- Task result storage
- Deduplication of identical jobs
- Failure classification
- Scan history and reproducibility metadata

Every task must carry its engagement identifier, operator identifier, scope configuration version, module version, and unique task identifier.

Rate Control

Implement token-bucket or leaky-bucket rate controls with Redis-backed coordination for distributed workers.

Allow administrators to define conservative request rates and concurrency limits by module and engagement. Apply backoff when a target returns rate-limit responses or indicates service stress. Do not implement mechanisms designed to evade a target's rate limits, access controls, or monitoring.

Evidence Chain

Every finding and asset observation should record:

- Unique evidence identifier
- Source module and source reference
- Collection timestamp
- Engagement and task identifiers
- Target asset identifier
- Observation type
- Confidence
- Evidence hash where appropriate
- Sanitized raw evidence
- Tool and module versions
- Relevant configuration
- Reproduction guidance for safe validation
- Analyst notes
- Evidence retention and deletion status

Use append-oriented audit records for important state changes. Prevent ordinary users from silently altering historical evidence.

7. VULNERABILITY INTELLIGENCE

CVE Correlation Engine

Integrate with authoritative and maintained vulnerability sources, such as:

- NIST National Vulnerability Database
- CISA Known Exploited Vulnerabilities catalog
- Vendor security advisories
- GitHub Security Advisories
- Other approved vulnerability intelligence providers

Features:

- Product and version normalization
- CPE mapping where applicable
- CVE lookup and enrichment
- CVSS and severity metadata
- Known-exploitation status where documented
- Vendor remediation references
- Affected-version ranges
- Evidence-to-CVE correlation
- Duplicate finding suppression
- Confidence and uncertainty reporting

A version match alone must not be presented as confirmation that a target is vulnerable. Distinguish:

1. Observed: The relevant technology or version was identified.
2. Potential: A vulnerability may apply based on available evidence.
3. Validated safely: A non-destructive check confirmed a specific security condition.
4. Needs manual verification: The available evidence is insufficient.

Exploit Reference Catalog

Provide a reference-only catalog of public advisories, vendor fixes, vulnerability descriptions, and responsible disclosure information.

For each reference, include:

- CVE or advisory identifier
- Affected product
- Vulnerability description
- Impact summary
- Known affected versions
- Patch or mitigation references
- Source and publication date
- Defensive detection guidance

Do not download, generate, execute, or chain exploit code against live targets. The interface may link to authoritative public advisories for analyst research without embedding automated exploitation.

Misconfiguration Assessment

Create a curated, reviewed set of non-destructive checks using Nuclei-compatible templates or native checks.

Assess areas such as:

- Publicly accessible storage configuration indicators
- Exposed administrative interfaces
- Unintended debug endpoints
- Weak security headers
- Insecure transport configuration
- Publicly exposed service metadata
- Unrestricted directory listing indicators
- Common cloud and container configuration mistakes

Every template must have a documented purpose, request profile, expected response size, risk classification, and safe validation method. Do not enable intrusive templates by default.

SSRF, XXE, and RCE Indicators

Provide non-destructive detection guidance and safe configuration checks.

- Identify suspicious input handling patterns from owner-provided source code.
- Review security headers, proxy configuration, and relevant application metadata.
- Use harmless, owner-controlled test endpoints in isolated environments when an interaction test is explicitly approved.
- Record evidence of a suspected issue without retrieving internal data or executing commands.
- Support manual verification notes and remediation tracking.

Do not probe cloud metadata services or internal network resources through a live application's request mechanism. Do not use payloads designed to execute commands, read files, or cause state changes.

Dependency Confusion and Supply Chain

Provide defensive supply-chain analysis:

- Parse package manifests and lockfiles.
- Identify dependency name collisions and suspicious namespace patterns.
- Compare package sources and registries.
- Detect dependency pinning weaknesses.
- Integrate with npm audit, OSV, Snyk, or equivalent configured services.
- Generate SBOMs with Syft where supported.
- Identify vulnerable dependencies and available fixes.

Do not publish packages, claim namespaces, alter registries, or attempt package takeover.

Isolated Fuzzing and Unknown Vulnerability Research

Provide a separate laboratory workflow for owner-controlled applications, local services, and intentionally vulnerable test targets.

Support:

- Bounded protocol and input fuzzing
- boofuzz and Radamsa integrations
- Test-case management
- Resource and execution limits
- Container or VM isolation
- Crash and anomaly capture
- Reproducibility metadata
- Regression test generation
- Sanitized crash reports
- Manual triage and responsible disclosure notes

Require an explicit lab designation and local or isolated target validation before execution. Disable production fuzzing by default. Do not include automated exploit generation, weaponization, or deployment of discovered vulnerabilities.

Build this as a defensive configuration and policy assessment module—not an account-access tool.

Password Policy Analyzer

Analyze owner-provided policy configuration and application source code for:

- Minimum and maximum length
- Password composition requirements
- Password reuse restrictions
- Known-compromised password screening configuration
- Password reset controls
- Account recovery configuration
- Password storage and hashing indicators
- Rate-limit and lockout policy configuration

Use synthetic examples for demonstrations. Do not test real users' passwords or attempt password guessing.

Authentication Configuration Audit

Review:

- MFA enrollment and enforcement configuration
- Recovery-flow security indicators
- Authentication error-message consistency
- Session lifetime and renewal configuration
- Cookie security attributes
- CSRF protections
- Account lockout and throttling configuration
- Password reset token design indicators
- OAuth and OpenID Connect configuration
- Authentication event logging

Where live checks are explicitly authorized, limit testing to harmless unauthenticated metadata and operator-provided test accounts with fixed, known credentials. Never perform credential spraying, credential stuffing, password brute force, OTP guessing, or automated account discovery.

OAuth and OpenID Connect

Check configuration and owner-provided metadata for:

- Redirect URI restrictions
- Issuer and audience validation configuration
- State and nonce handling indicators
- PKCE configuration
- Token lifetime settings
- Secure token storage patterns
- Scope configuration
- Public client configuration
- Discovery metadata consistency

Do not attempt to obtain, replay, steal, or use another user's token. Do not bypass authentication or authorization controls.

Session Security

Assess:

- Secure, HttpOnly, and SameSite cookie flags
- Session identifier rotation design
- Session expiration settings
- Logout and revocation behavior from configuration or owner-provided test evidence
- CSRF controls
- Session fixation risk indicators from code review
- Token storage patterns

Use synthetic sessions or designated test accounts in an isolated environment. Do not capture or reuse third-party session cookies or tokens.

SSH, RDP, FTP, and Database Services

Provide service identification, banner metadata, supported protocol information, and configuration checks.

- Detect service versions where safely observable.
- Identify insecure protocol configuration indicators.
- Compare observed versions with vendor advisories.
- Report exposed services and recommended access restrictions.
- Support owner-provided configuration-file analysis.

Do not attempt login guessing, password spraying, account enumeration, or unauthorized session creation.

Authentication Test Lab

Provide a self-contained demo environment with synthetic accounts and deliberately configured weak policies.

The lab may demonstrate defensive detection of:

- Excessive failed authentication attempts
- Missing throttling
- Inadequate lockout configuration
- Weak session expiration
- Insecure recovery settings

Use simulated event logs and controlled test cases. The lab must not contain reusable attack automation against real services.
